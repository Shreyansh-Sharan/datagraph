1. Scope and product

datagraph turns warehouse tables into a queryable knowledge graph. A builder drafts an ontology (with key inference or AI help), binds classes and attributes to tables and columns (an R2RML mapping compiled to SQL), builds the graph into Postgres, adds inference and quality rules, and publishes a version that people explore in the UI and agents query over MCP and GraphQL.

This document specifies the UI. It is the deliverable for a front-end team (or agent) that builds the interface against the existing REST API; it does not change the backend. Where the current single-page app already implements a feature, it is marked exists so the team can decide between reuse and rebuild.

Adapter requirement. The UI must treat Postgres and Databricks as the two primary source adapters. Every screen that touches warehouse data (catalog browsing, metadata, mapping, SQL preview, table preview, build, warehouse publishing) must work identically against both, show which adapter the deployment is running, and generate SQL in that adapter's dialect. Other warehouses (Fabric, SQL Server) come later through the same ports and must not require UI changes beyond a new label.

Users and jobs

Builder (data engineer)

  • Draft an ontology from tables, refine it, map it, build the graph, fix quality issues.
  • Works long sessions, keyboard-heavy, in an IDE-and-dashboards day.

Reviewer / domain expert

  • Reads the ontology map and the mapping status, comments, approves or rejects a version.
  • Needs the map to read without knowing RDF.

Explorer (analyst)

  • Finds an entity, sees what it connects to, follows relationships, spots hubs and communities.
  • Uses search, the graph stage and the triples grid.

Admin

  • Principals and roles, API keys, locks, MCP exposure per domain, the source adapter in use.

Non-goals

  • Marketing surface, mobile-first layouts (tablet-tolerant is enough), custom visual language for standard controls.
  • Editing the graph's triples by hand: the graph is always derived from the mapping and a build.
  • Drag-and-drop ontology editing on the canvas in the first release (see open items).

2. Architecture

The UI is a thin client. All state lives in the backend; the browser holds only the current route, the identity, and per-viewer conveniences (theme, last tab). The API is same-origin under /, the UI is served at /ui/.

Backend facts the UI can rely on

  • 121 REST routes under one FastAPI app; JSON errors as {"detail": "..."} with 400/401/403/404/409 semantics.
  • Builds are asynchronous (BuildScheduler); the run record is updated step by step so the UI can poll GET /builds/{run_id}.
  • Static UI assets are served with Cache-Control: no-cache (ETag revalidation) so a deploy is visible on reload.
  • Reference scale (live Databricks domain rgm, 17 tables): 263,695 triples, +23,207 inferred, 12,445 entities, 109k edges. The graph stage must stay fluid at this scale by sampling and expanding, never by loading everything.

3. Postgres and Databricks adapters

Required adapter-aware UI elements

  1. Source chip in the top bar exists: icon + Postgres or Databricks · <catalog>, tooltip "Source warehouse".
  2. Catalog browser (Metadata and Mapping): schema picker, searchable table list from GET /catalog/tables?schema_name=, column list with type, comment and key badges from GET /catalog/tables/{table}.
  3. Dialect-correct SQL in every SQL view, with a copy button.
  4. Adapter error surfacing: permission errors (e.g. Databricks INSUFFICIENT_PERMISSIONS on a catalog) must be shown verbatim with the action the user can take ("ask for USE CATALOG / USE SCHEMA / SELECT on …"), not as a generic failure.
  5. Settings → Source panel: read-only summary of the adapter (kind, catalog, schema, materialization mode, auth mode) and a "Test connection" that calls GET /catalog/tables and reports latency.

4. Domain model and lifecycle

Domain

  • name (slug), description, base_iri, review_quorum.
  • Has many versions; one may be active (served to MCP/GraphQL).
  • MCP policy: exposed, disabled_tools[].

Version

  • version number, status: draft → in_review → published → archived.
  • Content flags: has_ontology, has_mapping, has_r2rml, rule_count, constraint_count.
  • Editable only in draft; a builder takes a lease (lock) to edit.

Build run

  • status (queued/running/succeeded/failed/cancelled), steps[] with name, seconds, detail; triple_count, error.
  • Failed builds keep the previous graph.

Roles

  • viewer: read everything published.
  • builder: edit drafts, build, submit for review.
  • reviewer: approve/reject, publish, archive.
  • admin: principals, keys, locks, MCP policy.

Pipeline the UI must make visible

Every domain screen shows where the version is in Ontology › Mapping › Graph. The breadcrumb ticks each stage as it completes (has_ontology, mapping completion 100 %, last build succeeded) exists. A version that is missing a stage shows a next-step empty state instead of a blank screen.

Domains › rgm v1 › ✓ Ontology › ✓ Mapping › ✓ Graph [draft] ☰ My tasks 🛡 Admin ▦ Databricks · finops_metadata ☾ alice (admin)

7. Graph stage

One reusable WebGL component used by Ontology (map), Mapping (designer) and Explore. Current implementation: sigma.js 2.4 + graphology 0.25 + graphology-library 0.8, vendored (MIT). Any replacement must keep the contract below.

renderGraph(container, {
  nodes: [{ id, label, type, glyph?, color?, size? }],
  edges: [{ source, target, label?, kind?: "inheritance" }],
  selected?, colorBy?: "type" | "community", showEdgeLabels?, backdrop?, focusDim?, legend?,
  onSelect(node), onExpand(node), onContextMenu(node, items)
}) → { destroy, select(id), fit, highlight(ids), clearHighlight, has(id),
      setting(name, value), attrs(id), merge({ nodes, edges }), graph }
  • Layout: ForceAtlas2 with noverlap, incremental on merge; "Layout" button re-runs it; F fits.
  • Colour: stable palette by class with a legend (≤ 12 entries), or by Louvain community; explicit per-node colour wins (mapping status).
  • Backdrop mode (Explore): everything grey and label-less until hover, selection or a highlight set; then the neighbourhood lights up and the rest dims.
  • Focus-dim off (Ontology, Mapping): selection outlines the node without greying the rest, so status colours stay readable.
  • Interactions: hover highlights neighbourhood; click selects and opens the panel; double-click expands / opens the form; right-click context menu (expand, focus, hide, copy IRI); arrow keys move selection; Enter opens; Escape closes.
  • Clusters: detect (resolution slider), collapse into super-nodes with member counts, expand, clear; chips list the clusters.
  • Toolbar: zoom in/out, fit, layout, clusters, colour-by select, edge-labels toggle; status line "N nodes · M edges"; legend bottom-left.
  • Resilience: renders into a 0×0 container without error and fits once it gets a size; resizes with its container; hidden panels use [hidden] and must not leak outlines.
  • Scale: 1,500 nodes / 5,000 edges must stay above 30 fps on a 2020 laptop; larger sets are sampled server-side.

10. Non-functional requirements

AreaRequirement
PerformanceFirst screen interactive under 1 s on a warm cache; table grids virtualise beyond 200 rows; graph stage sampled server-side (≤ 1,500 nodes) and expanded on demand; Databricks calls show a skeleton within 100 ms and are cancellable.
StatesEvery data surface has loading, empty, error and permission-denied states. Errors show the backend detail verbatim plus a next step. 401 in token mode reopens the key prompt; 403 explains the role needed.
ConcurrencyEditing requires the lease; if another user holds it the editor is read-only with the holder's name and a "Request / force" action by role. 409 on save reloads and shows a diff-style message.
AccessibilityWCAG 2.1 AA: keyboard operable throughout (including the graph stage: arrows, Enter, F, Escape), visible focus, ARIA roles on tabs/dialogs/menus, aria-sort on sortable headers, live regions for build progress, 4.5:1 contrast.
ResponsivenessDesktop first (1280–1920). At ≤ 1400 px the top-bar labels collapse to icons; at ≤ 1024 px split panels stack; the app is tablet-tolerant, not mobile-first.
SecuritySecrets never reach the browser; API keys stored only in localStorage under the user's control; all SQL previews go through the backend's SELECT-only guard; table names for previews are validated server-side.
DeployabilityNo build step required (ES modules) or a single static bundle; served by the same FastAPI app under /ui; works behind Databricks Apps' forwarded-identity proxy and in Docker.
TestingBrowser smoke tests (agent-browser or Playwright) for each P0 screen against both adapters; contract tests pinned to the shapes in §8; visual checks of the graph stage at 400 and 1,500 nodes.

Acceptance criteria (release 1)

  • The source chip and the Settings → Source panel show the correct adapter, and "Test connection" reports latency or a verbatim permission error with the grant to request.
  • All SQL shown for the running adapter executes unchanged in that warehouse.
  • Explore renders the rgm graph (263k triples) with a sub-second first paint and expands any entity in under 500 ms after the API responds.
  • Every P0 screen passes keyboard-only operation and an axe-core scan with no serious violations, in both themes.

12. Open items

  • Typed sort in the triples grid is lexicographic on the literal text; a numeric sort needs a cast on the object column.
